Human-owned and reviewable input files.

- `05-discovery-brief.json`: single source of truth for the initial experiment brief
- `10-retrieval-request.json`: script-prepared or manually edited retrieval scope
- `11-med-aggregation-rules.json`: draft or human-authored MED grouping rules
- `12-probability-model-rules.json`: draft or human-authored probability rules
- `13-simulation-blueprint.json`: draft or human-authored backend mapping

## `05-discovery-brief.json` Field Guide

The discovery brief is a system-used input file.
It is not just descriptive text.

### Required fields

- `target_name`
  Human-readable target name used to anchor discovery.
  Example: `Bored Ape Yacht Club`

- `target_type`
  High-level target category used to shape retrieval and draft generation.
  Examples: `erc721_collection`, `governance_contract`, `defi_protocol`

- `goal`
  The main modeling goal.
  This is the most important natural-language field for downstream generation.

### Strongly recommended fields

- `questions`
  Short list of questions the experiment should answer.
  These help focus retrieval and later MED generation.

- `known_constraints`
  Hard constraints that the system should respect.
  Example: chain restrictions, evidence quality expectations, scope limits.

- `analysis_window`
  Default retrieval window for trend-oriented analytics.
  Example: `last_180_days`

- `preferred_metrics`
  Initial metric suggestions for Dune-side retrieval.
  These guide the first retrieval request draft.

### Optional fields

- `known_target.chain`
  Use when the chain is already known.

- `known_target.contract_address`
  Use when the contract address is already known.
  Leave `null` when the system must discover it.

- `known_target.contract_label`
  Friendly contract label when already known.

- `notes_for_ai`
  Extra hints that are useful but not central enough to belong in `goal` or `questions`.

## Minimal viable brief

At minimum, fill:

- `target_name`
- `target_type`
- `goal`

Everything else improves the quality of generated retrieval and draft modeling files.

## `10-retrieval-request.json` Field Guide

The retrieval request is the operational retrieval plan.
It is generated from the discovery brief and then reviewed by a human before live MCP usage.

### Role in the pipeline

- `05-discovery-brief.json` says what the experiment is trying to discover
- `10-retrieval-request.json` says what data must be retrieved
- `20-rendered-retrieval-prompts.json` turns the retrieval request into prompt payloads

### Required fields

- `experiment_id`
  Must match the experiment descriptor.

- `objective`
  Carries forward the top-level goal for traceability.

- `target.chain`
  Target chain for retrieval.

- `target.contract_address`
  Target contract address.

- `target.contract_label`
  Human-readable label for the target contract.

- `etherscan_request.template`
  Template path used for Etherscan-side retrieval.

- `etherscan_request.required_outputs`
  Structured list of expected contract-side outputs.

- `dune_request.template`
  Template path used for Dune-side retrieval.

- `dune_request.analysis_window`
  Time window used for analytics retrieval.

- `dune_request.target_metrics`
  Metrics that Dune-side retrieval must focus on.

### Optional fields

- `discovery_goal`
  Expanded text carried from the discovery brief.
  Useful for traceability and for prompt-generation context.

### Who writes it

- initially generated by `prepare:retrieval-request`
- then reviewed and optionally edited by a human

### Who uses it

- `render:retrieval-prompts`
- humans preparing live MCP retrieval

### When to modify it

Modify it when:

- the inferred contract target is wrong
- the chain is wrong
- the requested Etherscan outputs are incomplete
- the Dune metrics are poorly aligned with the experiment
- the analysis window is not appropriate
